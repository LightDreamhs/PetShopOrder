## 1. 现状盘点：单店假设在哪里

系统当前是典型的"单店单机"轻量单体，**全库没有任何店铺/租户维度**（grep `shop_id`/`store_id`/`tenant` 零命中）。多店改造前，先列出所有隐含"全局只有一家店"的硬编码点：

| # | 位置 | 单店假设 | 多店下的含义 |
|---|---|---|---|
| 1 | 16 张表 | 全部无 `shop_id` | 商品、订单、会员等无法区分门店 |
| 2 | `system_config` | 单行表（id=1），存店铺坐标、配送半径/起送价、预约营业时段、收款码、开屏广告、企微 webhook | 每家店都需要独立一份 |
| 3 | `system_config_delivery_tier` | 分段运费挂在 `config_id=1` 下 | 每店独立运费分段 |
| 4 | `OrderServiceImpl.java:129` | `deliveryService.calculateDeliveryFee(distanceKm, 1L)` 硬编码配置 id=1 | 需改为按当前店铺取配置 |
| 5 | `admin_user.role`（BOSS/MANAGER/STAFF） | 角色即全局权限，无店铺归属 | 店长/店员只能看本店数据，BOSS 跨店 |
| 6 | `member`/`member_level`/`member_phone` | 全局一套会员体系 | 连锁场景下各店会员独立（或总部通级） |
| 7 | `PriceCalculationServiceImpl.resolveDiscountRate(phone)` | 按手机号全局命中会员 | 需改为按店命中会员 |
| 8 | `sku`（价格/会员价/库存） | 全局一份价格 | 各店可独立定价、上下架 |
| 9 | `FileServiceImpl` 上传 | 本地磁盘单一目录 `uploads/` | 按店铺分目录，避免文件混杂 |
| 10 | `NotificationServiceImpl` | 全局一个企微/飞书 webhook | 各店订单通知到各店的群 |
| 11 | 根目录 `店铺二维码.png` | 一张静态二维码 | 每店一张，需系统生成 |
| 12 | Sa-Token 内存会话 | 单实例、重启全员掉线 | 多店后重启影响全部门店，需 Redis 化 |
| 13 | 部署（单机三容器、手工部署、无 CI/CD） | 服务一家店 | 发布影响所有店，需更强的发布纪律与备份 |

> **说明**：库存（`sku.stock`）目前只是展示字段，**全项目没有下单扣减库存的逻辑**。本规划不强制引入库存扣减（见第 11 节），但"店铺 SKU"模型为其留好了位置。

## 2. 总体架构决策

### 2.1 核心决策一览

| 决策点 | 结论 | 理由 |
|---|---|---|
| 租户模型 | 共库共表 + `shop_id` 字段，`ShopContext`（ThreadLocal）承载当前店铺 | ≤ 10 家店，单库完全够用；不引入 MyBatis-Plus 改写插件，手写 SQL 逐条补条件，风险可控 |
| 用户体系 | `app_user` **平台级**（手机号全局唯一）；`member`/`member_level`/`member_phone` **店铺级** | 顾客跨店无需重复注册；会员权益按店独立。"总部统一通级"留作后期可选增强 |
| 商品模型 | **平台商品目录 + 店铺 SKU**（推荐，见 2.2 对比） | 连锁商品基本一致，避免 10 家店重复维护同一份目录；店长只管价格、库存、上下架 |
| 店铺配置 | 新建 `shop_config`（每店一行，承接现 `system_config` 全部字段）+ `shop_delivery_tier`；`system_config` 三张表退役 | 现有 `system_config` 所有字段均为店铺级，无全局残留；1:1 迁移现有页面与服务 |
| 权限模型 | `admin_user` 加 `shop_id`（NULL = 总部）；BOSS 跨全店，MANAGER/STAFF 绑定单店 | 一人管多店时建多个账号，不做"一人多店"关联表（≤ 10 家不需要） |
| 店铺识别（C 端） | 每店专属二维码 URL `https://2zg.site/?s={code}`，请求头 `X-Shop-Code` 携带当前店 | 先用路径/参数方案，不动 DNS、证书、地图 key 白名单（见 6.2 对比） |
| 订单号 | 保持 `"PS" + 日期 + 雪花后 8 位`，全局唯一 | 唯一索引已保证不冲突，无需加店铺前缀 |
| 会话 | 引入 Redis + sa-token-redis（Phase 4） | 重启不掉线是全店诉求；也是未来多实例的前提 |

### 2.2 商品模型对比

| 方案 | 做法 | 改造量 | 适用场景 |
|---|---|---|---|
| **A. 平台目录 + 店铺 SKU（推荐）** | `product`/`main_service_addon` 保持平台级，总部维护；`sku` 加 `shop_id` + `status`，价格/会员价/库存/上下架按店 | 中：ProductPage 拆"总部商品目录"与"本店 SKU 管理"两层 | 连锁各店商品基本一致、价格可微调 —— 本项目预期场景 |
| B. 每店独立商品 | `product`、`sku` 都加 `shop_id`，每店完整维护商品+SKU | 最小：只加字段，页面加过滤 | 各店商品差异极大、无总部统一诉求 |

> **推荐 A 的理由**：10 家店重复录入同一份商品/服务目录是持续的运营负担；总部统一上新品、下架停售，店长只调价格与库存，符合连锁管控直觉。

## 3. 数据库改造设计（MySQL）

### 3.1 新增表 DDL 草案

```sql
-- 门店（身份 + 坐标 + 状态）
CREATE TABLE IF NOT EXISTS shop (
    id            BIGINT AUTO_INCREMENT PRIMARY KEY,
    code          VARCHAR(32)   NOT NULL COMMENT '店铺编码，二维码/URL 识别用，如 main、pudong',
    name          VARCHAR(64)   NOT NULL COMMENT '店铺名称',
    phone         VARCHAR(20)   NULL COMMENT '门店电话',
    address       VARCHAR(255)  NULL COMMENT '门店地址（展示用）',
    shop_lat      DECIMAL(10,7) NOT NULL COMMENT '纬度（配送中心）',
    shop_lng      DECIMAL(10,7) NOT NULL COMMENT '经度',
    status        VARCHAR(16)   NOT NULL DEFAULT 'OPEN' COMMENT 'OPEN 营业 / CLOSED 歇业',
    sort          INT           NOT NULL DEFAULT 0,
    create_time   DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP,
    update_time   DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    UNIQUE KEY uk_shop_code (code)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='门店';

-- 店铺配置（每店一行，字段沿用现 system_config，1:1 迁移）
CREATE TABLE IF NOT EXISTS shop_config (
    id                  BIGINT AUTO_INCREMENT PRIMARY KEY,
    shop_id             BIGINT        NOT NULL,
    delivery_radius_km  DECIMAL(5,2)  NOT NULL COMMENT '配送半径',
    delivery_min_amount DECIMAL(10,2) NOT NULL COMMENT '起送价',
    delivery_fee_type   VARCHAR(16)   NOT NULL DEFAULT 'FREE' COMMENT 'FREE / TIERED',
    order_time_enabled  TINYINT(1)    NOT NULL DEFAULT 0,
    order_start_time    TIME          NULL,
    order_end_time      TIME          NULL,
    qywx_webhook_url_enc VARCHAR(512) NULL COMMENT '本店订单通知 webhook（AES 加密）',
    has_qywx_webhook    TINYINT(1)    NOT NULL DEFAULT 0,
    payment_qr_url      VARCHAR(255)  NULL COMMENT '本店收款码',
    ad_enabled          TINYINT(1)    NOT NULL DEFAULT 0,
    ad_image_url        VARCHAR(255)  NULL,
    ad_link_type        VARCHAR(16)   NULL,
    ad_link_target      VARCHAR(255)  NULL,
    updated_by          BIGINT        NULL,
    create_time         DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP,
    update_time         DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    UNIQUE KEY uk_shop_config (shop_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='店铺配置';

-- 店铺分段运费（沿用 system_config_delivery_tier 结构，挂 shop_id）
CREATE TABLE IF NOT EXISTS shop_delivery_tier (
    id             BIGINT AUTO_INCREMENT PRIMARY KEY,
    shop_id        BIGINT       NOT NULL,
    min_distance_km DECIMAL(5,2) NOT NULL,
    max_distance_km DECIMAL(5,2) NOT NULL,
    fee            DECIMAL(10,2) NOT NULL,
    sort           INT          NOT NULL DEFAULT 0,
    create_time    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    update_time    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    INDEX idx_tier_shop (shop_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='店铺分段运费';
```

> **注意**：现 `system_config.fixed_delivery_fee` 已下线（前端无入口），不再迁移；开屏广告 4 个字段（`migration_ad_v1.sql` 加入）按店铺迁移到 `shop_config`。`system_config` / `system_config_delivery_tier` / `system_config_log` 三表退役，配置变更审计复用 `operation_log`。

### 3.2 业务表加 `shop_id` 清单

| 表 | 改造 | 说明 |
|---|---|---|
| `sku` | + `shop_id` NOT NULL、+ `status`（ON_SALE/OFF_SALE，默认 ON_SALE） | 店铺级价格/会员价/库存/上下架；商品上下架仍在 `product.status`（总部） |
| `orders` | + `shop_id` NOT NULL | 订单归属店；下单时从 ShopContext 写入 |
| `order_item` | + `shop_id` NOT NULL（冗余） | 按店统计明细免 JOIN |
| `appointment` | + `shop_id` NOT NULL | 预约归属店；冲突检查、营业时段校验按店 |
| `member` / `member_level` / `member_phone` | 各 + `shop_id` NOT NULL | 店铺会员体系；等级、折扣率按店定义 |
| `admin_user` | + `shop_id` NULL | NULL=总部（BOSS）；MANAGER/STAFF 绑定单店 |
| `operation_log` | + `shop_id` NULL | NULL=总部操作；便于按店审计 |
| `product` / `main_service_addon` | **不加**（平台级） | 方案 A：总部统一维护商品目录与主/附加服务绑定 |
| `app_user` / `user_address` | **不加**（平台级） | 顾客与地址跨店通用；地址是否可达由各店配送半径运行时判断 |

### 3.3 索引与唯一约束改造

| 表 | 改造 |
|---|---|
| `orders` | 新增 `INDEX idx_orders_shop_create (shop_id, create_time)`、`INDEX idx_orders_shop_processed (shop_id, processed)` |
| `sku` | 新增 `UNIQUE KEY uk_sku_shop_product_spec (shop_id, product_id, spec_name)`、`INDEX idx_sku_shop_product (shop_id, product_id)` |
| `appointment` | 时间段冲突检查索引改为带 `shop_id` 前缀：`(shop_id, start_time, end_time)` |
| `member_phone` | 唯一约束从 `phone` 改为 `(shop_id, phone)` —— 同一手机号可在不同店对应不同会员 |
| `admin_user` | `username` 保持**全局唯一**（登录无需先选店） |

> 其余查询索引在 Phase 1 联调后按 `EXPLAIN` 结果补充，原则：所有按店查询的索引都应含 `shop_id` 前缀。

### 3.4 迁移脚本策略

新增 `backend/sql/migration_multi_store_v1.sql`（模式与 `migration_ad_v1.sql` 一致，同步并入 `init.sql`）：

1. 创建 `shop` / `shop_config` / `shop_delivery_tier` 三表。
2. 插入默认店 `id=1, code='main'`（名称用现有门店实名），从 `system_config` id=1 行**拷贝**全部店铺级字段到 `shop_config`，拷贝分段运费到 `shop_delivery_tier`。
3. 各业务表 `ADD COLUMN shop_id BIGINT NOT NULL DEFAULT 1`（存量数据一步归入默认店），`admin_user`、`operation_log` 用 `ADD COLUMN shop_id BIGINT NULL`。
4. `sku` 加 `status` 列默认 `ON_SALE`。
5. 重建 `member_phone` 唯一约束、补充 3.3 节索引。
6. **不删旧表**：`system_config` 三表保留一个版本周期，代码切换并验证后再下线。

> **警告**：生产 MySQL 数据卷已"冻结" `init.sql` 的首次执行结果（见 `deploy/GO-LIVE-CHECKLIST.md` 第 7 节已知行为），新表/新列必须手动执行迁移脚本，修改 `init.sql` 不会自动生效。迁移前先执行一次全量备份（见 7.4）。

## 4. 后端改造设计

### 4.1 租户上下文与店铺解析

新增 `common/ShopContext.java`（ThreadLocal）与 `interceptor/ShopResolveInterceptor.java`，注册进现有 `WebMvcConfig`：

- **C 端 `/api/app/**`**：从请求头 `X-Shop-Code` 解析店铺编码（缺失时回退默认店并记 WARN）；校验店铺存在，写入 `ShopContext`。当前店由前端持久化（localStorage + cookie），未登录用户也可多店浏览。下单、预约等写接口额外校验店铺 `OPEN` 状态。
- **管理端 `/api/admin/**`**：从 Sa-Token 登录态取员工 `shopId`（BOSS 为 NULL 可通过请求头 `X-Shop-Id` 切换，服务端校验其角色后才写入上下文；MANAGER/STAFF 忽略切换请求）。
- 拦截器 `afterCompletion` 中 `ShopContext.clear()`，防止线程池复用导致串店。

| `MemberMapper.xml` / `MemberLevelMapper.xml` / `MemberPhoneMapper.xml` | 全部查询/写入加 `shop_id` |
| `StatsMapper.xml` | 全部统计加店铺维度；BOSS 汇总视图用"全部店"分支 |
| `SystemConfigMapper.xml` / `SystemConfigDeliveryTierMapper.xml` / `SystemConfigLogMapper.xml` | 改造为 `ShopConfigMapper` / `ShopDeliveryTierMapper`，按 `shop_id` 读写 |

### 4.4 认证与权限

- `admin_user.shop_id` 落库后，登录响应返回员工角色 + 店铺归属；`StpInterfaceImpl` 维持角色模型不变。
- 数据权限在 **service 层**收敛：MANAGER/STAFF 的一切查询强制 `shopId = 员工.shop_id`（来自登录态，不信任请求参数）；BOSS 可传 `shopId` 参数或传空看全部。
- 新增切店能力：`GET /api/admin/shops/current`、`PUT /api/admin/shops/current {shopId}`（仅 BOSS），切换结果由前端存 Pinia 并在请求头 `X-Shop-Id` 携带。

### 4.5 新增后端接口清单

| 接口 | 端 | 说明 |
|---|---|---|
| `GET/POST/PUT /api/admin/shops`（+ 状态启停） | Admin | 店铺 CRUD（BOSS）；建店时自动生成默认 `shop_config`。**已裁剪（开店时再做）**；Phase 1 已实现 GET 列表与 `/current` 两个只读接口 |
| `GET/PUT /api/admin/shops/{id}/config` | Admin | 店铺配置读写（迁移自现 SystemConfig 接口） |

## 6. 服务器部署规划

### 6.1 目标拓扑变化

| 项 | 现状 | 目标 |
|---|---|---|
| 容器 | mysql + backend + frontend(nginx) | + **redis:7-alpine**（共 4 容器） |
| 会话 | Sa-Token 内存（重启全员掉线） | sa-token-redis-jackson + spring-boot-starter-data-redis，重启不掉线 |
| 文件 | `/data/petshop/uploads` 单目录 | 同目录下按 `shop-{id}/` 分区（nginx 配置不变） |
| 部署方式 | 手工 `git pull` + `docker compose up -d --build` | 先一键脚本化，见 6.4 |
| 备份 | mysqldump cron（30 天保留） | 保留 + 异地备份，见 6.3 |

> **容量评估**：≤ 10 家店、C 端用户 ≤ 2000、同时在线 ≤ 500，单机（现有腾讯云实例）+ MySQL 单实例完全够用；不需要读写分离、分库分表。Redis 引入的目的**不是性能**，而是会话持久化与未来多实例的可选性。

### 6.2 店铺识别与域名策略

| 方案 | URL 形态 | 前置工作 | 结论 |
|---|---|---|---|
| **路径/参数（推荐）** | `https://2zg.site/?s=pudong` | 无（DNS、Let's Encrypt 证书、腾讯地图 key 白名单均不动） | Phase 1~3 采用 |
| 子域名 | `pudong.2zg.site` | 泛解析 `*.2zg.site` + wildcard 证书（DNS-01 验证）+ nginx 泛 `server_name` + 腾讯地图白名单补充 | 店数 > 20 或品牌诉求时再演进 |

### 6.3 备份与容灾

- 保留现有 cron：`mysqldump --single-transaction` 每日全量 + uploads 打包，30 天保留。
- 新增**异地备份**（强烈建议，多店后数据责任变重）：每日备份产物用 `coscli`/`rclone` 上传腾讯云 COS，COS 侧开 90 天生命周期。
- 每季度做一次**恢复演练**（备份文件导入临时容器验证可查），演练记录写入 `deploy/README.md`。

### 6.4 发布流程（CI/CD）

多店后每次发布影响所有门店，"手工 SSH + 敲命令"的风险被放大。最小可行方案：

1. 新增 `deploy/deploy.sh`：`git pull` → `docker compose ... up -d --build` → `curl /health` 健康检查 → 失败自动回退旧镜像（compose 记录上一镜像 tag）。
2. 进阶（可选）：若仓库托管在 GitHub，加 GitHub Actions 在 push master 时构建镜像并通过 SSH 在服务器执行 `deploy.sh`。

### 6.5 监控

- 保留 backend `HEALTHCHECK` 与 nginx `/health`。
- 新增外部拨测（如 UptimeRobot 免费版）监控 `https://2zg.site/health`，异常时通知企微/飞书群。
- 日志暂用 `docker logs` + Docker 默认轮转，不上日志平台（规模不需要）。

## 7. 数据迁移与上线演练

1. **演练**：本地用生产备份还原一份数据，执行 `migration_multi_store_v1.sql`，验证本节末尾的回归测试清单。
2. **生产迁移窗口**：选低峰时段，顺序为"全量备份 → 执行迁移脚本 → 发布新版本 backend → 冒烟验证"。迁移脚本与新版本 backend 必须**同窗口上线**（旧代码读 `system_config`、新代码读 `shop_config`，跨窗口会出现配置读取不一致）。
3. **上线后**：`system_config` 三表保留观察一个版本周期，确认无依赖后下线。

### 回归测试清单（双店数据环境）

- [ ] 两家店各自建商品/SKU/会员等级，互不可见（总部切店可见）。
- [ ] A 店顾客下单：计价按 A 店 SKU、运费按 A 店分段、订单落 A 店。
- [ ] 同一手机号在 A 店是会员、B 店不是：A 店享折扣、B 店原价。
- [ ] B 店店长登录：订单/会员/预约/统计仅本店；无法切店。
- [ ] BOSS 切店后各页面数据跟随；看全部汇总正确。
- [ ] 各店 webhook 只收本店订单通知。
- [ ] A 店歇业（CLOSED）时 H5 可浏览但不可下单/预约。
- [ ] 无 `X-Shop-Code` 请求回退默认店；历史订单/图片 URL 不受影响。

## 9. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 漏加 `shop_id` 条件导致**串店**（最严重） | A 店用户看到 B 店数据 | 4.2 清单逐条核对；回归测试必须用双店数据环境；Code Review 检查项新增"新 SQL 是否带店铺条件" |
| ThreadLocal 泄漏/未清理 | 线程复用串店 | 拦截器 `afterCompletion` 强制 clear；禁止业务代码在自建线程中使用 ShopContext |
| C 端店铺被伪造 | 数据越权查看 | C 端店铺本就是公开信息，风险低；写接口校验店铺 OPEN；管理端切店校验角色与归属，绝不信任前端参数 |
| 迁移脚本与代码版本错配 | 配置读取不一致/启动失败 | 第 7 节：迁移脚本与新版 backend 同窗口上线；上线前备份 |
| 商品拆层（方案 A）带来页面复杂度 | 店长误改全局商品 | 权限收敛：商品目录仅 BOSS/总部可写；店长仅见本店 SKU 管理 |
| 单机故障影响全部门店 | 全店不可用 | Phase 4 备份/监控强化；≤10 家规模接受单机风险，不主动上多机（见第 10 节） |

## 10. 明确不做的事（YAGNI）

- ❌ SaaS 多商家入驻、租户计费、入驻审核（形态为连锁直营）
- ❌ 分库分表 / 每店独立 schema / 每店独立部署（≤ 10 家，共库共表足够）
- ❌ 微服务拆分（保持单体）
- ❌ "一人多店"员工关联表（一人管多店建多个账号即可）
- ❌ 会员"总部通级"（先按店独立，业务提出需求再做增强）
- ❌ 促销/营销活动（需求已于 2026-09 取消；设计方案存档于《促销套餐设计方案.md》，未来重启时可基于本规划的店铺 SKU 模型实施）
- ❌ 店铺 CRUD 管理界面与店铺二维码接口（两店且短期不开新店；开店时执行一次性「开店初始化 SQL」并走第 7 节回归清单验证，界面届时再补）
- ❌ 库存扣减/防超卖（现状无此逻辑；店铺 SKU 模型为未来引入铺路，需时单独设计）
- ❌ MyBatis-Plus 租户插件改写 SQL（手写补条件，规模可控、行为可预测）
- ❌ 读写分离、多实例负载均衡（Redis 就绪后随时可加，当前无必要）
